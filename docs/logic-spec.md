# Arcanum · спецификация логики и данных

Алгоритмический слой: формулы, структуры данных, правила использования собранного.
product-spec отвечает «что видит пользователь», этот файл — «как это считается и где хранится».
Менять алгоритм → сначала правка здесь. Все примеры проверяемы — использовать их как тест-кейсы.

## 1. Карта дня

**Выбор.** При первом запуске генерируется `installSeed` (случайное число 0–2^31, в store, живёт вечно).
Карта дня: `index = hash(dateISO + ':' + installSeed) % 78`, hash — FNV-1a 32-bit. Свойства:
у каждого пользователя своя карта; в течение дня не меняется (переустановка приложения = новый seed —
допустимо); заранее «подсмотреть» завтрашнюю нельзя только честностью — не показываем.
**Анти-повтор.** Если выбранная карта уже выпадала в последние 7 дней (по history) →
`index = hash(index + ':retry:' + n) % 78`, n=1,2,… до карты вне окна (максимум 10 попыток, дальше — как есть).
**Перевёрнутые: в карте дня НЕ используются в v1** (новичков не пугаем, трактовка дня всегда прямая).
Подтверждено редактором 13.08 (editor-questions, вопрос 6) — это решение, а не недоделка.
Перевёрнутые живут в раскладах: там каждая карта reversed с вероятностью 30%.

**1б. Состав расклада — офлайн-анализ БЕЗ ИИ (решение 09.08: ИИ в v1 не используем).**
После открытия всех карт показываем блок «Состав расклада»: 1–4 детерминированных наблюдения
по правилам (проверяются в этом порядке, берутся первые сработавшие):
1. Доля Старших арканов ≥ половины карт → «X из N карт — Старшие арканы: расклад о значимых
   поворотах, а не о повседневных мелочах».
2. Одна масть ≥ половины младших карт → фраза масти: Жезлы — о деле и энергии · Кубки — о чувствах
   и отношениях · Мечи — о мыслях и решениях · Пентакли — о материальном и опоре.
3. Перевёрнутых ≥ половины → «Многое в раскладе перевёрнуто: темы в процессе переосмысления».
4. Совпадение номиналов (2+ карты одного номера) → «Две/три <номинала>: тема повторяется —
   обратите на неё внимание» (тузы — начала, десятки — завершения, придворные — люди и роли).
5. Если ничего не сработало → «Состав ровный: каждая позиция говорит сама за себя».
**Точные пороги (спека 36):** majors — `2·m ≥ n`; масть — младших ≥2, лидер единственный, `best ≥ 2`
и `2·best ≥ младших`; reversed — `2·r ≥ n`; номиналы — ОДНО наблюдение на правило: группы
aces/tens/courts (все придворные вместе)/generic 2–9, счёт ≥2, побеждает наибольший, при равенстве
aces → tens → courts → номиналы по возрастанию. Наблюдений может быть от 1 до 4 (все сработавшие
по порядку); нейтральную не добиваем — «Преобладают Кубки» + «Состав ровный» противоречили бы
друг другу. Реализовано ✅: `src/lib/composition.ts` (`analyzeSpread`/`compositionTexts`), выбор
варианта — общий `pickVariant` (§9), `{rank}` — из `rankNames` composition.json.
**Язык наблюдений — строго нейтральный** (политика сторов + наша редполитика): констатация состава +
вопрос для размышления («Спросите себя: …»). ЗАПРЕЩЕНО: советы действий, предсказания событий,
темы здоровья/денег в формулировках наблюдений. **Шаблоны фраз — content/composition.json** (ru/en,
20 фраз: по 2–3 варианта на каждое правило; редактируются женой как обычный контент). Вариант
выбирается ДЕТЕРМИНИРОВАННО: hash(дата расклада + имя правила) % число вариантов — при повторном
открытии расклада из дневника текст не меняется. Math.random для текста не использовать.
ИИ-разбор: НЕ обещаем в UI (никаких «скоро»); вернёмся к вопросу отдельно после запуска и первых
скачиваний — решение за Артёмом и женой.

**1а. Выбор карт в раскладе.** Тасуем все 78 (Fisher–Yates на Math.random — криптостойкость не нужна),
берём первые N по позициям расклада: одна карта НЕ может выпасть дважды в одном раскладе.
Каждой выпавшей — reversed с вероятностью 0.30 (независимо). Карты открываются по одной тапом,
порядок позиций — как в spreads.json. Перетянуть карты нельзя (расклад честный); новый расклад —
новое тасование. Сохранение: `SpreadDraw = {ts, date, spreadId, cards: [{cardId, reversed}] (в порядке
позиций), question?, note?}` в spreadsHistory (лимит 100, §7) — `ts` (мс тасования) = идентификатор
записи (в день бывает несколько раскладов). Реализовано ✅ (спека 36): `src/lib/spread.ts` —
`dealSpread(count, rng)`; тест-кейсы там же. Тест-кейсы: в 1000 раскладов «Кельтский крест» нет дублей
внутри расклада; доля reversed по всем картам 30% ±3п.п.
**Смена даты на устройстве** не детектим (v1): дата берётся с устройства, манипуляции — на совести пользователя.
**Тест-кейс:** seed=42, дата 2026-08-08 → каждый запуск в этот день даёт один и тот же index.

## 2. Серия (streak)

Открытие карты дня = событие серии (единственное в v1; уроки серию НЕ двигают — ритуал один).
`lastDrawDate == вчера → streak+1; иначе → streak=1`. Часовой пояс устройства, границы дня — локальная полночь.
**Заморозка ✅(10):** стартовый запас 1 (и у существующих установок после обновления); +1
начисляется 1-го числа месяца, потолок 2 (`FREEZE_MAX`). Начисление ленивое — при первом
открытии приложения в новом месяце (гидрация + возврат из фона, `syncFreezeGrant`);
пропущенные месяцы доначисляются по одному, потолок общий. Пропуск ровно одного дня и
freezes>0 → при следующем открытии карты: freezes−1, streak+1 (пропущенный день в счёт не
входит: 5 → пропуск → 6), на «Сегодня» весь день строка «Серию спасла заморозка»
(`freezeSpentDate`), утром дня после пропуска — пуш `freeze` вместо утреннего (§8).
Пропуск 2+ дней подряд → сброс в 1 (заморозка не тратится). Чистые функции —
`src/lib/streak.ts` (advanceStreak/grantFreezes). Тест-кейсы: 5 → пропуск 1 дня (freezes 1)
→ 6; пропуск 2 дней (freezes 2) → 1, заморозки целы; месяцы 05→08 с нуля → 2.
**Вехи** (ачивки + предложение оценить приложение): 3, 7, 14, 30, 60, 100 дней.

## 3. Рефлексия «как прошёл день с картой» — сбор И ИСПОЛЬЗОВАНИЕ

**Сбор.** С 18:00 на «Сегодня»; пуш в 21:00 если нет ответа и карта открыта.
**Отключение:** настройка «Вечерняя рефлексия» (вкл по умолчанию). Выкл → блок не показывается,
вечерний пуш не планируется, накопленные данные и статистика остаются (сводки считаются по дням
с ответами). Independент от тумблера пушей: можно оставить блок без пуша. Данные в записи history:
`outcome: 'yes'|'partly'|'no'` + `note: string` (≤500 симв.). Ответ можно изменить до полуночи, потом фиксация.

**Использование (все три места — v1, вместе с задачей 05/06):**
1. **Дневник (профиль):** отметка ✓/≈/✗ у каждой записи + заметка.
2. **Сводка месяца (шапка дневника):** «Карта месяца: Луна (4 раза)» — мода по cardId за календарный месяц;
   «Отозвалось 12 из 18 дней» — счёт outcome yes+partly / всего ответов. Слово «отозвалось» (НЕ «сбылось
   предсказание» — мы про рефлексию, не про гадание; важно для тона и для ревью сторов).
3. **Личная история на странице карты:** блок «Ваша история с картой» (если выпадала ≥1 раза):
   «Выпадала 4 раза · отзывалась 3» + последняя заметка. Данные: фильтр history по cardId.
**НЕ делаем** (осознанно): выводы типа «карты говорят правду в 80%», сравнение с другими пользователями.
**Аналитика (PostHog, к запуску):** событие reflection_answered {outcome} — измеряем вовлечённость вечерней петли.

## 4. XP и уровни

Источники XP (v1): открытие карты дня +5 · первый ответ рефлексии за день +3 (смена ответа до
полуночи повторно не начисляет) · урок: 10 − 2×ошибки, мин 4 ·
повторное прохождение урока +2 (раз в день на урок) — дата награждённого повтора в
`lessonsProgress[id].repeatDate` · расклад +5 — при **сохранении в дневник** (не при открытии всех
карт: иначе XP фармится циклом «открыл → ушёл без сохранения», спека 36) · повторение: +1 за
вспомненную карту (оценка ≥1 карты, которая была к повторению; спека 45, §12).
Уровни: 1→2: 50 XP; 2→3: 150; 3→4: 300; 4→5: 500; далее каждый +250. Даунгрейда нет, XP не сгорает.
Названия уровней (RU): 1 Любопытная · 2 Ученица · 3 Читающая · 4 Толковательница · 5 Хранительница ·
6+ Мастерица (EN: Curious/Student/Reader/Interpreter/Keeper/Adept).

## 5. Аркан рождения

Сумма ВСЕХ цифр даты ДД.ММ.ГГГГ; пока результат >22 — суммировать его цифры; 22 → Дурак (0), иначе аркан 1–21.
**Тест-кейсы:** 15.03.1994 → 1+5+0+3+1+9+9+4=32 → 3+2=5 → Иерофант (V).

## 6. Луна: фазы, лунный день, события

Локальный расчёт без сети, точные моменты (задача 47, заменила «среднюю луну» от эпохи 2000):
моменты новолуния и полнолуния считаются по Meeus, *Astronomical Algorithms*, гл. 49 — средняя
фаза лунации k + периодические поправки + 14 планетных членов, ΔT = 69 с константой, точность
~1–2 минуты (формулы и 18 опорных эфемерид — спека 47, раздел А; тесты `moon.test.ts`,
допуск ±2 мин — не шире: при ±10 сьют оставался зелёным на перепутанном знаке ΔT). Средняя луна давала до ±14 ч к реальному моменту — для строки фазы терпимо,
для календаря с датами нет.
**Фаза** — окна СИММЕТРИЧНЫЕ вокруг точных моментов (hf-01, 09.08): новолуние — |t − момент
новолуния| < 0.92 сут; полнолуние — |t − момент полнолуния| < 0.92 сут; между окнами растущая
(от новолуния к полнолунию) и убывающая. **Лунный день** = floor(возраст) + 1, возраст — сутки
от последнего новолуния; лунация 29.27–29.83 сут, поэтому день 30 бывает не в каждом месяце.
**Событие календаря** (экран `/moon`) — один ЛОКАЛЬНЫЙ календарный день точного момента, показывается
с местным временем («Новолуние · 12 августа · 20:37»); окно фазы (~2 суток «Новолуние» в строке
«Сегодня») — период, событие — момент, это разные вещи и не противоречат друг другу. Месяц
содержит 1–3 события (в феврале может не быть полнолуния, в длинном месяце — два новолуния).
Начало недели в сетке — по языку (`WEEK_START`: ru — ПН, en/es/pt — ВС, CLDR выбранных локалей).
Тест-кейсы (UTC): 23.08.2025 06:06 — новолуние · 09.08.2025 07:55 — полнолуние · 12.08.2026 17:37 —
новолуние (затмение) · 28.08.2026 04:18 — полнолуние · 28.08.2025 — растущая · 15.08.2025 — убывающая.
Использование v1: строка на «Сегодня» (нажимаема → `/moon`), экран лунного календаря; пуши
новолуния/полнолуния — §8 (задача 47б); окно лунных раскладов — ниже (задача 51).

**Окно лунного расклада (51).** Расклад события доступен в локальный день события ПЛЮС сутки до
и сутки после — то есть три полных локальных дня, границы по локальной полуночи. Чистое правило —
`src/lib/moonSpread.ts`: `isMoonWindowOpen(at, now)` отвечает про КОНКРЕТНОЕ событие (нужна панели
под строкой события), `moonSpreadState(kind, now)` — про актуальное событие своего вида (нужна
карточке в списке и гейту маршрута, где конкретного события нет). Источник событий инъектируется,
как у `monthEvents` (47) и `moonDaysIn` (47б).

⚠️ **Окно считается КАЛЕНДАРНЫМИ сутками, а не ±24 часами от точного момента** — решение спеки 51,
и оно осознанное. Причины три: всё приложение живёт локальными днями (граница дня карты дня hf-01,
SRS 45, лунный пуш 47б), и окно, закрывающееся в 21:36 посреди вечера, было бы единственным
исключением; человек, получивший утром пуш «Полнолуние ✦», обязан весь этот день видеть расклад
открытым, а при ±24 ч от момента 04:18 он захлопнулся бы в 04:18 следующего дня; и наконец,
границы по полуночи проверяются тестами с литералами дат, а не вычислением того же кода.
Ширина окна — одна константа `MOON_WINDOW_DAYS = 1`.

⚠️ **Сохранённая запись окном не ограничена никогда** — дневник обязан открываться и через полгода;
гейт стоит только на игровом маршруте `/spreads/[id]`, а не в `app/spread/[ts].tsx`.

## 7. Хранение (все данные локально)

AsyncStorage, ключ `arcanum-app` (zustand persist), схема (сейчас `version: 10`):
`{ schemaVersion: 3, installSeed, profile: {name?, birthDate?, birthArcanaId?, onboarded}, themeMode, lang,
streak, lastDrawDate, freezes, freezeMonth, freezeSpentDate, xp, history: DailyDraw[365],
lessonsProgress: {lessonId: {done, errors, ts, repeatDate?}},
spreadsHistory: SpreadDraw[100], settings: {reflectionOn: true, pushesOn: true, pushMorning: '09:00',
pushEvening: '21:00', pushAsked: false},
srs: {cardId: {reps, intervalDays, ease, due}}, reviewDay: {date, newCount} }`
`DailyDraw = {date, cardId, reversed: false, outcome?, note?}`.
**Миграции:** schemaVersion обязателен; при повышении версии — функция migrate в store (без потери history).
⚠️ **Ловушка поверхностного слияния `settings`.** `zustand/persist` сливает сохранённое состояние
с дефолтом ТОЛЬКО по верхнему уровню ключей: сохранённый `settings: {reflectionOn: false}` заменит
объект-дефолт `settings` целиком, а не сольётся с ним по ключам — полей, которых не было в момент
сохранения, у уже установленного приложения само по себе не появится. Поэтому каждая задача,
добавляющая поле в `settings` (06а подняла `version` до 2 ради `reflectionOn`; 06б подняла до 3,
добавив `pushesOn`/`pushMorning`/`pushEvening`/`pushAsked`; следующая задача с новым полем
в `settings` поднимает версию по общему правилу, сформулированному ниже в этом разделе),
обязана поднять `version` персиста и дописать недостающие
ключи руками в `migrate` — иначе новые настройки не появятся у пользователей, обновившихся
с более старой версии. **Реализовано (06б):** правило вынесено в чистый модуль `src/lib/settings.ts` —
`DEFAULT_SETTINGS` + `mergeSettings(saved)` (дописывает отсутствующие ключи); `migrate` стора
зовёт `mergeSettings` напрямую, а не держит слияние второй копией.
**07 подняла `version` до 4** ради поля `lessonsProgress` — но это ключ ВЕРХНЕГО уровня состояния,
а не вложенность внутри `settings`, поэтому отдельная ветка миграции ему не нужна: поверхностное
слияние persist подставляет дефолт `{}` само (ловушка выше бьёт только по вложенным объектам
вроде `settings`, где слияние идёт лишь по их собственному верхнему уровню ключей).
**08 подняла `version` до 5** ради поля `xp` — ключ верхнего уровня, дефолт 0 доливается
поверхностным слиянием сам; `repeatDate` живёт внутри записей `lessonsProgress` и опционален —
миграция не нужна.
**09 подняла `version` до 6** ради поля `profile` — снова ключ верхнего уровня, дефолт
`{ onboarded: false }` доливается поверхностным слиянием сам, поэтому у уже установленного приложения
онбординг покажется ровно один раз, а серия/дневник/XP не тронутся. ⚠️ Но `profile` — ВТОРОЙ
вложенный объект состояния после `settings`, и ловушка выше распространяется на него целиком:
задача, которая добавит поле ВНУТРЬ `profile` (ближайший кандидат — 16, «предложить дату, если
пропущена»), обязана поднять версию И дописать слияние руками, как это сделано для `settings`.
**10 подняла `version` до 7** ради полей `freezeMonth` и `freezeSpentDate` (плюс новый дефолт
`freezes: 1` вместо прежнего 0) — `v7: freezes, freezeMonth, freezeSpentDate (спека 10)`, все три
ключи ВЕРХНЕГО уровня состояния, дефолты (`1`/`null`/`null`) доливаются поверхностным слиянием
сами, `migrate` руками не правился. Существующие установки получают `freezes: 1` сразу
(решение спеки 10).
**27 подняла `version` до 8** ради расширения домена `lang`: тип вырос с двух значений до четырёх
(`ru`/`en`/`es`/`pt`, единственное объявление — `src/lib/lang.ts`), но сама форма схемы не
изменилась — `lang` уже был ключом верхнего уровня, отдельной ветки миграции не потребовалось.
Версия поднята не ради данных, а ради честной ошибки: файл бэкапа с испанским или португальским
языком, попавший в старую сборку, обязан получить отказ «более новая версия», а не выглядеть
повреждённым. Язык первой установки определяется по списку предпочтений устройства среди языков,
ДОСТУПНЫХ в приложении, в момент первой гидрации — тем же моментом, что и назначение личного сида
(`installSeed`); дальше язык слушается только пользователя. **Восстановление из бэкапа язык

## 9. Выбор варианта текста (правило вариативности)

Для всех текстов с пулом вариантов (content/phrases.json, composition.json, будущие variants блоков карт):
`index = fnv1a(dateISO + ':' + textKey) % variants.length`. Свойства: в течение дня формулировка
стабильна (открыл повторно — тот же текст), на следующий день — как правило другая; для расклада
вместо dateISO — дата расклада (текст в дневнике не меняется никогда). Math.random для выбора
текста ЗАПРЕЩЁН. Плейсхолдеры {name}, {card}, {n}, {days} подставляются после выбора варианта.
{days} — готовая плюрализованная строка вида «3 дня»/«5 дней» (собрана i18next ДО подстановки,
в `pushBody`), а не сырое число: используется в `push.streak_save`, где подстановка {n} напрямую
дала бы неправильное согласование («Серия 3 дней»); если писать новый русский вариант этой фразы,
число дней подставлять только через {days}, не через {n}.
Тест-кейс: один день + один ключ → 100 вызовов → один и тот же вариант.

## 8. Пуши (расписание)

Все локальные (expo-notifications), сервера нет. Утренний (settings.pushMorning, деф. 9:00): «Ваша карта
уже ждёт ✦» — не отправляется, если карта дня уже открыта. Вечерний (21:00): «Как прошёл день с <картой>?» —
только если карта открыта и рефлексии нет. Спасение серии: 20:00, если карта не открыта и streak ≥3
(«Серия 12 дней — ещё можно спасти»). Возврат: 3+ дня тишины → 1 пуш «Луна скучала» (один раз, не спамим).
`freeze` (10): утро дня после первого пропущенного дня, ЗАМЕНА утреннего слота (не добавка) —
условия `freezes > 0` и `streak ≥ 1`; текст — приглашение вернуться (`push.freeze_saved`,
3 варианта), а НЕ отчёт о свершившемся: заморозка тратится только при открытии карты, и пуш
уходит ДО этого момента, пока спасение ещё не случилось (не откроют карту вовсе — серия назавтра
сгорит). Несёт `n = streak` ДО спасения (после открытия станет `streak+1`; в тексте подставляется
готовой формой через `{days}`). Приоритет при конфликте: спасение серии > вечерняя рефлексия.
`moon` (47б): в локальный день новолуния/полнолуния — тоже ЗАМЕНА утреннего слота (правило
master-plan «вместо, а не поверх», число пушей в день не меняется), тот же час; текст и заголовок
берутся по виду события (`push.moon_new`/`push.moon_full`, `push.titleMoonNew`/`push.titleMoonFull`).
Freeze-день лунной заменой не перекрывается: его ветка в `planPushes` стоит раньше `moon`,
спасение серии функционально и праздником не подменяется. Возвратный пуш лунным не подменяется.
Максимум 2 пуша/день — жёсткий инвариант; приоритет при обрезке: `streak`
(спасение серии) > `evening` (вечерний) > `freeze` > `moon` > `morning` (утренний) > `comeback` (возврат).

**Как это реализовано (06б).** План считается заново на каждое изменение состояния и ставится
конкретными датами (`SchedulableTriggerInputTypes.DATE`), а не повторяющимся DAILY: система
уведомлений условий не проверяет, а три правила из четырёх условные. Горизонт — от сегодня: утренние на
3 дня вперёд, на 4-й день один возвратный, дальше тишина до возвращения. Вечерний и спасение серии
ставятся ТОЛЬКО на сегодня (вечерний называет карту по имени, а откроют ли завтрашнюю — неизвестно;
серия после пропущенного дня уже сброшена). Приоритет при обрезке до 2 пушей в день: спасение серии >
вечерний > `freeze` > `moon` > утренний > возврат (10 добавила `freeze` третьим, 47б — `moon`
четвёртым). Чистые правила без единого импорта expo/react, план возвращает ключи
фраз из `content/phrases.json`, а не готовый текст — `src/lib/pushPlan.ts` (под юнит-тестами; счётчик тестов держим в одном месте — AGENTS.md, здесь он трижды протухал); работа
с системой — `src/lib/pushes.ts` (единственный модуль, знающий про `expo-notifications`).
Пересчёт запускает `src/lib/usePushScheduler.ts`. Технически эффект висит на `settings`, `streak`,
`history` и `lang` ЦЕЛИКОМ (объектами, не отдельными полями), поэтому честно он пересчитывается
на любое изменение любого из них, а не строго в шести именованных точках — например, на заметку
в дневнике (меняет `history`) или смену языка (меняет `lang`) тоже, хотя план от этого не
меняется, просто пересчитывается заново без надобности. Именованных точек, ради которых эта
зависимость и заведена, шесть:

1. гидрация стора (первый рендер после чтения persist);
2. возврат приложения из фона (`src/lib/useAppActive.ts` — `useFocusEffect` возврат из фона
   не ловит, см. CLAUDE.md);
3. открытие карты дня;
4. ответ рефлексии;
5. смена настроек (тумблер, время, `pushesOn`);
6. ответ на системный запрос разрешения в прелюдии («Сегодня»). Флаг `settings.pushAsked`
   ставится ТОЛЬКО после того, как `requestPermission()` резолвится, а не в момент показа
   диалога — если бы флаг менялся раньше, `settings` поменялся бы, пока ОС ещё не ответила
   (`'undetermined'`), эффект перепланировал бы на этом устаревшем значении и погасил бы всё,
   а настоящий ответ ОС уже был бы некому передать дальше (ни одна зависимость эффекта больше
   не меняется). Этот баг и правку нашло финальное ревью 06б.

⚠️ **`expo-notifications` и `@react-native-community/datetimepicker` не имеют веб-реализации** —
весь адаптер в `pushes.ts` на вебе не-операция. `getPermission()` на вебе намеренно отдаёт
`'undetermined'`, а не `'denied'`: `'denied'` в коде экрана настроек означает «спрятать блок
и открыть системные настройки по тапу», а `Linking.openSettings` в react-native-web не существует
(TypeScript этого не ловит — тип берётся из react-native и платформенно-независим). Отдать здесь
`'denied'` сделало бы блок напоминаний невидимым в браузере и обнулило бы веб-проверку задачи.

⚠️ **Прочитанные из ОС уведомления не несут форму триггера, с которой были поставлены.** Android
отдаёт `{type: 'date', repeats, value}`, iOS конвертирует DATE-триггер в `{type: 'timeInterval',
seconds, repeats}` — декодировать обратно ненадёжно. DEV-диалог «План пушей» в настройках поэтому
показывает СВОЙ насчитанный план (те же данные, что берёт живой планировщик — общая сборка
`planInputFromStore`), а из системы берёт только count дожидающихся уведомлений; расхождение
числа строк плана со счётчиком — сигнал, что перепланирование не долетело до ОС.

⚠️ **Холодный старт планирует дважды.** Эффект `usePushScheduler` срабатывает и на
дефолтном состоянии стора (до гидрации), и сразу следом на настоящем — оба запуска делают
«отменить всё и поставить план заново», не атомарно. Без сериализации это гонка: `applyPlan`
клеймит каждый вызов растущим номером и ставит вызовы в цепочку, устаревший вызов бросает свою
работу, если пока ждал очереди подоспел более новый пересчёт; `initPushes` держит промис
инициализации (не булев флаг), чтобы конкурентные вызовы дожидались ОДНОЙ настоящей настройки
Android-канала, а не гонялись мимо неё.

## 10. Числительные (плюрализация)

**Правило для любого нового ключа с числом: русскому обязательны ТРИ формы `_one/_few/_many`,
английскому — две `_one/_other`.** Ключ вида `«{{count}} урока»` без форм — это баг, который
на устройстве покажется по-английски, а в браузере будет выглядеть правильно.

Почему так строго (hf-02, 13.08). Формы выбирает `Intl.PluralRules` — механизм самого движка JS.
В браузере он полный, **в Hermes на телефоне его нет**. Не получив ответа, i18next 26 молча берёт
встроенную заглушку «1 → one, всё остальное → other», ищет `ключ_other`, не находит его в русском,
не находит и голый ключ — и уходит на `fallbackLng: "en"`. Пользователь видит «6 MODULES · 32 LESSONS»
в русском интерфейсе. Отсюда живучесть бага: при count = 1 строка остаётся русской, ломается
начиная с 2.

Лечение — полифилл `intl-pluralrules`, импортируется первой строкой `src/lib/i18n.ts` (пакет ставит
себя только когда движок не тянет правила сам, поэтому веб и устройство считают формы одинаково).
Разбор: `docs/specs/hf-02-plurals-research.md`, решение: `docs/specs/hf-02-hermes-plurals.md`.

Исключение из правила — ключи, где рядом с числом нет склоняемого слова: `settings.queuedCount`
(«В очереди системы: 5»), `journal.withNote` («5 с заметкой»). Они перечислены белым списком
в `src/lib/__tests__/i18nPlurals.test.ts`; добавляя туда новый ключ, объясняйте почему.

Число, которое подставляется в чужую фразу как готовая строка, плюрализуется ДО подстановки —
см. `{days}` в §9.

⚠️ **Юнит-тест обычного вида это не ловит**: jest гоняется на Node, у которого полный ICU.
Тест обязан сносить `Intl.PluralRules` до загрузки `i18n.ts` — иначе он зелёный и на сломанном коде.
⚠️ **Веб-проверка (6а/6б) слепа к этому классу багов в принципе.** Достоверна для композиции,
отступов, логики и поведения; НЕ достоверна для всего, что считает сам движок JS: формы
числительных, форматы дат, локальные форматы чисел. Единственный судья — пункт 6в, устройство.

## 11. Готовность контента и что показывать (спека 28а, 19.08)

**Статус готовности принадлежит паре «единица контента + язык».** В файле это словарь
`"status": {"ru": "reviewed", "en": "draft"}`; языка нет в словаре — значит `todo`.
Единицы: блок значений карты, слова карты (`wordsStatus` — один на `name`+`keywords`+`search`),
теория урока, `quizStatus` урока, статус staging-файла викторины.

**Текст берётся `inLang` с фолбэком на английский, а готовность спрашивается у ТОГО ЯЗЫКА,
который реально попал на экран** — `statusIn(block, lang)` / `blockText(block, lang)`
в `src/lib/content.ts`. Спрашивать статус выбранного пользователем языка нельзя: пока перевода
на испанский нет, испанец видит английский текст, и проверка испанского статуса нарисовала бы
ему «Текст готовится» поверх готового текста. Обратная ошибка (спросить статус английского,
показав испанский) дала бы черновик под видом готового.

Каскада у статуса нет: если показан язык, у которого `todo`, показывается заглушка, и точка.
Состояние «текст на языке есть, а статус у него `todo`» в бандл не попадает — связку
«есть текст ⟺ статус не `todo`» держит контракт-тест `src/lib/__tests__/cardsContent.test.ts`.

⚠️ **Отсутствие ключа языка и пустая строка значат РАЗНОЕ.** `presentLang` считает язык
присутствующим по `!== undefined`, поэтому `"es": ""` — это «испанский есть, и он пустой»,
и пользователь получит пустое место вместо готового английского текста. Конвейеру запрещено
создавать `es`/`pt` пустыми заглушками; отдельный контракт-тест это стережёт.

Зачем схема менялась: до 19.08 статус был один на все языки, и `reviewed`, поставленный
редактором за русский, молча распространялся на английский. Английский канон в итоге не читал
никто до задачи 31, где на него пришлось 44 правки из 110.

## 12. Повторение изученных карт — SM-2 (спека 45, 19.08)

**Колода** = карты пройденных уроков в порядке курса (`deckOrder` = `learnedCardIds`); карта без
записи в `srs` — новая. **Алгоритм** SM-2 по ЛОКАЛЬНЫМ ДНЯМ (`due` — ISO-день, не timestamp):
оценки 0 не помню / 1 с трудом (в UI нет) / 2 помню / 3 легко → q = 1/3/4/5; q < 3 → reps 0,
интервал 0, due = сегодня (карта возвращается в конец сессии); q ≥ 3 → reps+1, интервал
1 → 6 → round(prev × ease) (ease ДО обновления), потолок 365; ease' = clamp(ease + (0.1 − (5−q)·
(0.08 + (5−q)·0.02)), 1.3, 5) при любой оценке; новая карта стартует с ease 2.5.
**Сессия** ≤ 10: просроченные по due ↑, потом новые в порядке колоды (не больше 10 новых в день —
`reviewDay.newCount` по дате), итог тасуется; новая карта всегда «карта → значение», повторяемая
— 50/50. «Не помню» ставит карту в хвост очереди сессии.
**XP** (`XP_REVIEW = 1`): +1 за оценку ≥1 карты, которая до оценки была к повторению (новая или
due ≤ сегодня); правило без понятия «сессия» — провал и затем «помню» дают +1, повторное «помню»
уже ушедшей карты — 0. **Сводка** для карточки курса: due / newAvailable / dueTomorrow (`due ≤
завтра`, показывается только при due = 0).
Тест-кейсы: `srs.test.ts` (лестница 1/6/15, ease по оценкам, потолки, провал), `review.test.ts`
(12 просроченных → 10 старших; 3 + 20 новых → 3 + 7; лимит новых по дате; инвариант «сумма gained
= sessionStats.xp» на сценарии с двумя провалами; `promptSentence` + контракт по 78 картам).
Хранение — §7 (`srs`, `reviewDay`, persist 10); бэкап валидирует коридоры (ease 1.3..5, интервал
≤ 365, id из колоды, ≤ 78 записей).
**Экраны (спека 45б):** карточка «Повторение» — `reviewCardState(summary)` даёт `hidden` (колода
пуста) / `due` (есть просроченные) / `new` (просроченных нет, есть доступные новые) / `done` (по
приоритету, в этом порядке); ссылка «Ещё N» — `nextSessionSize(summary) = min(SESSION_MAX, due +
newAvailable)` (согласие с тем, сколько карт реально соберёт `buildSession` на той же сводке —
под тестом). Подсказка направления `toCard` — `maskCardName(promptSentence(general), name)`:
первое предложение `general` у ВСЕХ 78 карт начинается с имени карты (ru) или содержит его (en),
без маскировки рубашка-вопрос выдавала бы ответ; корпусный контракт проверяет отсутствие имени
в подсказке по всем 78 картам × ru/en.
