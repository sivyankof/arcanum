# Спека 11 · Экспорт/импорт данных (бэкап)

Статус: ЗАКРЫТА 14.08 — веб-проверка 6а/6б и лайв-проверка на iPhone пройдены ✓, влита в main · Поведение: product-spec §5 (настройки) ·
Схема данных: logic-spec §7 · Мотивация: master-plan §3.1-Р п.21 («смена телефона не должна
стирать месяцы дневника — источник гневных отзывов»)

## Цель

Пользователь может сохранить все свои данные в один файл и восстановить их из этого файла
на другом (или том же) устройстве. Закрывается риск «сменила телефон — потеряла дневник».

## Решения брейншторма (14.08, согласованы Артёмом)

1. **Бэкап — весь стор целиком**, а не только дневник: дневник, серия, заморозки, XP,
   прогресс курса, профиль (имя/дата рождения/аркан), настройки, installSeed. Master-plan
   п.21 прямо говорит «дневника И прогресса»; частичный бэкап всё равно оборачивается потерей.
2. **Импорт = полная замена** текущего состояния с явным предупреждением в `ConfirmDialog`.
   Слияние по датам/ключам отклонено: заметно сложнее в коде и в объяснении пользователю,
   больше краевых случаев, а сценарий задачи — восстановление на чистом устройстве.
3. **Канал — файл**: экспорт через системный share sheet, импорт через системный выбор файла
   (вариант А брейншторма). Вариант «JSON текстом через `Share.share` + вставка из буфера»
   отклонён (приёмники шара обрезают длинный текст, вставка руками — способ импортировать
   обрезок); облачный бэкап противоречит правилу «бэкенда нет и в v1 не будет».
4. **Валидация строгая, «всё или ничего»**: любой дефект файла — отказ целиком с человеческим
   сообщением. Мягкая фильтрация битых записей молча теряла бы данные — ровно то, от чего
   задача защищает.
5. **Persist version НЕ поднимается** (остаётся 7): схема стора не меняется, задача только
   читает и пишет её. Правило «следующая задача, меняющая схему, поднимает до 8» остаётся
   в силе для следующих задач.

## Формат файла

Читаемый JSON, имя `arcanum-backup-YYYY-MM-DD.json` (дата локальная, как везде в проекте):

```json
{
  "app": "arcanum",
  "kind": "backup",
  "schemaVersion": 7,
  "exportedAt": "2026-08-14T12:34:56.000Z",
  "state": { "…персистуемые ключи стора…" }
}
```

- `schemaVersion` = версия zustand persist на момент экспорта (сейчас 7, logic-spec §7).
- `state` — ЯВНЫЙ белый список ключей: `themeMode, lang, installSeed, streak, lastDrawDate,
  freezes, freezeMonth, freezeSpentDate, history, lessonsProgress, xp, settings, profile`.
  **Без `devReflect`** — dev-поле в бэкап не попадает.
- ⚠️ Чтобы будущие поля стора не выпадали из бэкапа молча — контракт-тест: «белый список =
  ключи персистуемого состояния минус dev-поля». Задача, добавившая поле в стор, обязана
  либо внести его в список, либо явно причислить к dev-полям — иначе тест красный.

## Валидация при импорте (порядок проверок)

1. Текст не разбирается как JSON, либо нет конверта (`app !== 'arcanum'` или
   `kind !== 'backup'`, `schemaVersion` не число, `state` не объект) → отказ
   «Файл не похож на бэкап Arcanum».
2. `schemaVersion` **больше** текущей версии persist → отказ «Файл создан в более новой
   версии приложения — обновите приложение». Накатывать схему из будущего нельзя:
   поля, которых текущий код не знает, прошли бы валидацию молча.
3. `schemaVersion` меньше или равна текущей → та же доливка, что у гидрации persist:
   поверхностное слияние с дефолтами по верхнему уровню + `mergeSettings` для вложенного
   `settings` (ловушка поверхностного слияния из logic-spec §7 применяется буквально).
   Старый бэкап получает новые поля так же, как получило бы обновившееся приложение.
4. Структурная проверка типов ВСЕХ полей белого списка; записи `history` — объекты
   `{date: 'YYYY-MM-DD', cardId: существует в колоде, reversed: boolean, outcome?: 'yes'|'partly'|'no',
   note?: string}`; лимиты logic-spec §7 (history ≤ 365) — превышение это дефект файла, отказ.
   Любое несоответствие → отказ целиком «Файл повреждён».

Ошибки `parseBackup` возвращает КОДАМИ (ключи i18n), а не готовым текстом — тот же приём,
что `pushPlan` (план отдаёт ключи фраз). Тексты — в `i18n.ts`, оба языка.

## Механика замены (импорт)

Новый экшен стора `restoreBackup(state)`:

1. `set(валидированное состояние)` — persist сам записывает в AsyncStorage; экшены стора
   при `setState`-слиянии сохраняются.
2. Защита `installSeed === 0` (файл добит руками/очень старый) → назначить новый сид,
   как это делает `onRehydrateStorage`.
3. `syncFreezeGrant()` — бэкап прошлого месяца сразу доначисляет заморозку нового.

Что происходит само, без нового кода (проверить в 6б, а не программировать):

- план пушей пересчитывается: `usePushScheduler` подписан на стор;
- тема и язык применяются немедленно: корневой layout синхронизирует i18n при смене `lang`;
- гейт онбординга: в бэкапе `profile.onboarded: true` → онбординг не показывается;
  бэкап, снятый ДО онбординга, честно вернёт на онбординг.

## UI (экран настроек)

Две строки `SettingsRow` после блока пушей, до DEV-блока:

- **«Экспорт данных»** (иконка `share-outline`): тап → собрать файл → системный share sheet.
  Промежуточных диалогов нет — share sheet и есть выбор «куда». Веб: файл скачивается браузером.
- **«Импорт из файла»** (иконка `folder-open-outline`): тап → системный выбор файла →
  валидация → при успехе `ConfirmDialog` (тон danger):
  заголовок «Восстановить данные?», текст-сводка из файла — дата бэкапа, число записей
  дневника, серия — и предупреждение «Текущие данные будут заменены». Подтверждение →
  `restoreBackup` → диалог «Данные восстановлены» (accent, одна кнопка).
  Ошибка валидации → диалог с одной кнопкой и текстом ошибки.
- Мелкое расширение `ConfirmDialog`: `cancelLabel`/`onCancel` становятся опциональными —
  без них кнопка отмены не рендерится (режим «сообщение»). Нужен диалогам ошибки и успеха;
  отдельный компонент не заводим.

⚠️ Правило 6а-0: product-spec §5 называет строку «Экспорт дневника 🔨(11)» — файл несёт
весь прогресс, поэтому строка называется «Экспорт данных»; product-spec поправить на шаге
синхронизации этой задачи.

## Файлы и пакеты

- `src/lib/backup.ts` (новый) — чистый модуль без импортов expo/react: `buildBackup(state, exportedAt)`,
  `parseBackup(text, currentVersion)` (результат: либо валидированное состояние, либо код ошибки),
  `backupFileName(dateISO)`, `backupSummary(state)` для сводки диалога. Юнит-тесты.
- `src/lib/backupIo.ts` + `src/lib/backupIo.web.ts` (новые) — вся платформенная файловая часть,
  приём `pushes.ts`/`pushes.web.ts`: натив — записать во временный файл (`expo-file-system`,
  кэш-папка) и отдать в `expo-sharing`; выбрать и прочитать файл (`expo-document-picker` +
  `readAsStringAsync`); веб — скачивание Blob-ссылкой и `<input type="file">` + FileReader.
- `src/store/useApp.ts` — экшен `restoreBackup` (version не трогается).
- `app/settings.tsx` — две строки + диалоги подтверждения/успеха/ошибки.
- `src/components/ConfirmDialog.tsx` — опциональная кнопка отмены.
- `src/lib/i18n.ts` — строки ru/en (названия строк, тексты диалогов, тексты ошибок).
- `package.json` — `npx expo install expo-file-system expo-sharing expo-document-picker`
  (все три входят в Expo Go SDK 54, мажорные версии не трогаются).
  ⚠️ Артёму: нужен `npm install` и перезапуск `npx expo start --tunnel`.

## Что НЕ делаем

- Облачный бэкап, автобэкап по расписанию, напоминание «давно не делали бэкап» — v1 без этого.
- Слияние данных при импорте — только полная замена.
- Шифрование/пароль на файл — данные локальные, файл остаётся у пользователя.
- Экспорт месяца текстом «поделиться» — это другая фича (product-spec §5, этап 3+).
- Импорт файлов из БУДУЩИХ версий схемы (отказ с сообщением — см. валидацию, п. 2).

## Тесты (`src/lib/__tests__/backup.test.ts`)

- Круговой: `buildBackup` → сериализация → `parseBackup` → состояние эквивалентно исходному.
- Отказы: не-JSON; чужой JSON без конверта; `schemaVersion` больше текущей; битая запись
  `history` (дата не ISO, неизвестный `cardId`, лишний тип); history длиннее 365.
- Доливка старой версии: бэкап со `settings` уровня v2 (только `reflectionOn`) после импорта
  получает все поля пушей из `DEFAULT_SETTINGS` через `mergeSettings`.
- `devReflect` в бэкап не попадает.
- Контракт-тест белого списка: ключи бэкапа = персистуемые ключи стора минус dev-поля
  (красный, если будущая задача добавит поле в стор и не решит судьбу его бэкапа).
